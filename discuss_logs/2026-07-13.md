# SceneZeroV2 下一阶段开发方案

## 一、当前实现判断

根据 `dev_logs/2026-07-13.md` 与当前 V2 代码，本轮录音已经具备真实电平波形、可靠时长、原生播放和本地文件导入。下一阶段不建议继续优先打磨录音视觉，而应把资源投入到 SceneZero 的核心差异：**从现实画面与 AR 场景事实，生成可解释、可编辑、可验证的提示词和创作建议**。

当前 Prompt 并非完全预制，但仍有四个根本限制：

1. `StructuredPrompt` 只有四段字符串，没有稳定的字段模型，无法逐字段编辑、比较和演进。
2. 人物与道具大多只进入数量摘要，具体预设、位置、朝向和尺度没有进入最终描述。
3. `SceneObjectRecord` 使用相对第一个放置对象的坐标，却没有保存拍摄瞬间的相机姿态，因此不能可靠推导画面左/右、前景/背景和主体朝向。
4. `PromptDocument` 与 `ARPrevisualization` 已建模，但保存链仍主要写 `Inspiration.prompt` 和 `layoutJSON`，新模型尚未成为事实来源。

创作建议目前只有三条本地条件文案：“保留灯光方向 / 保留空间纵深 / 记录人物关系”。它适合作为离线兜底，但还不是根据具体画面提出的建议系统。

## 二、产品原则

### 1. AI 不替用户决定表达

AI 的角色应是“观察、追问、提出可执行选择”，不是自动把画面包装成统一的电影腔。建议必须区分：

- 已观察事实：来自相机、AR 对象和用户输入；
- 推断：模型对画面或情绪的解释；
- 建议：用户可以接受、忽略或改写的动作。

### 2. 本地能力永远可用

无网、API 失败或用户不愿上传画面时，仍应能由本地规则生成完整的基础 Prompt。大模型负责理解画面、补充语义、提出问题和生成表达变体，不负责保存唯一真相。

### 3. 拍摄阶段轻，拍后阶段深

实时取景只提供一到三条短、具体、可执行的建议。复杂故事梳理、镜头衔接和 Prompt 改写放到拍摄确认页或灵感详情，避免在相机界面制造认知负担。

## 三、先建立可靠的场景事实层

### Phase A：新增纯 Swift 领域模型

不要让 UI、SwiftData 模型和 API JSON 共用同一个类型。建议新增：

- `SceneSnapshot`：一次拍摄不可变的事实快照；
- `CameraSnapshot`：相机世界变换、朝向、焦距、画幅和景别；
- `SceneEntitySnapshot`：人物/道具/灯光的稳定 ID、类型、预设、世界坐标、相机坐标、旋转和尺度；
- `LightingSnapshot`：灯位、方向、色温、强度和范围；
- `CreatorIntent`：用户的故事、情绪、关系、希望保留与不希望出现的内容；
- `PromptDraft`：可编码、可编辑的结构化 Prompt；
- `CreativeSuggestion`：观察、理由、建议动作、适用类别和置信说明。

`SceneSnapshot` 必须在按下快门时一次性生成，不能在之后重新读取仍在变化的 `ARSceneController` 状态。

### Phase B：补齐坐标与关系计算

拍摄时保存 `ARCamera.transform`，将每个实体的世界坐标转换到相机坐标系，再由确定性代码计算：

- 画面左 / 中 / 右；
- 前景 / 中景 / 背景；
- 人物与道具的前后、左右、接近与分离；
- 角色朝向相机、背向相机或侧向；
- 灯光相对主体的方向，而不只是灯光预设名称。

建议使用阈值枚举而不是把原始浮点坐标交给模型。例如 `horizontalZone = leading`、`depthZone = foreground`，并把阈值集中在一个可测试的 `SpatialRelationResolver` 中。

### Phase C：事实来源迁移

新写入路径应同时完成：

1. `SceneSnapshot` 编码为 `ARPrevisualization.layoutData`；
2. `PromptDraft` 编码为 `PromptDocument.structuredData`；
3. `PromptDocument.canonicalText` 保存当前可复制版本；
4. `Inspiration.prompt` 与 `layoutJSON` 暂时只作为兼容投影，下一 Schema 版本再删除。

这一步需要建立 `SceneZeroSchemaV2` 和轻量迁移，不能直接修改已经发布的 V1 Schema 定义。

## 四、结构化提示词生成设计

### 1. PromptDraft 建议字段

```text
PromptDraft
├── subject              主体、数量、身份占位和状态
├── action               动作或静态关系；未知时为空
├── environment          现场环境与时间线索
├── composition          左右、前中后景、空间层次
├── camera               画幅、焦距、景别、视角
├── lighting             灯位、色温、强度、范围
├── visualStyle          用户明确选择的质感与颜色
├── emotionalIntent      用户想表达的情绪
├── narrativeIntent      故事或人物关系
├── motionSuggestion     可选的摄影机/主体运动建议
├── mustPreserve         必须保留的事实
├── avoid                不希望模型擅自添加或改变的内容
└── uncertainties        系统无法确认、需要用户决定的部分
```

不要默认生成“生活痕迹、电影感、故事感”等审美词。只有用户选择、画面分析有依据，或用户接受建议后才写入。

### 2. 两级生成器

#### 本地确定性生成器

`LocalPromptCompiler` 从 `SceneSnapshot + CreatorIntent` 生成完整 `PromptDraft`：

- 不联网；
- 输出稳定、可单元测试；
- 不虚构人物动作、天气、场景和情绪；
- 作为所有模型调用失败时的最终结果。

#### 模型增强生成器

`RemotePromptEnhancer` 接收参考图、`SceneSnapshot` 和 `CreatorIntent`，只允许：

- 补充画面中可观察但 AR 没记录的环境信息；
- 把机械事实改写成自然镜头语言；
- 提供 2–3 个不同强度的表达方向；
- 标记不确定项并提出问题。

模型不能删除或修改 `mustPreserve` 中的事实。服务端返回必须符合与 `PromptDraft` 对应的严格 JSON Schema，再由客户端解码；不要让客户端解析自由文本标题。

### 3. 平台导出

Sora、Runway、可灵等格式应该由 `PromptRenderer` 从同一个 `PromptDraft` 派生，而不是分别调用模型生成。平台模板只决定字段顺序、语言和长度，不改变事实。

建议把平台适配声明为配置数据并记录版本，例如 `rendererID = sora`、`rendererVersion = 2`，以便未来模型规则变化后仍知道旧 Prompt 如何生成。

## 五、创作建议系统

### 1. 建议的数据结构

每条建议至少包含：

```text
CreativeSuggestion
├── category       composition / lighting / emotion / story / transition
├── observation    系统看到什么
├── suggestion     用户可以做什么
├── rationale      为什么可能有帮助
├── action         可选的可执行参数变化
├── source         localRule / model
└── confidence     certain / inferred / exploratory
```

不要显示伪精确的百分比置信度。“确定事实 / 画面推断 / 探索方向”更容易理解。

### 2. 相机中的本地实时建议

由 `LocalCreativeAdvisor` 根据场景状态事件触发，而不是逐帧运行：

- 新增或移动主体；
- 灯位或镜头设置变化；
- AR 追踪稳定；
- 用户主动点击灯泡。

建议在状态稳定约 500–800ms 后计算，每次最多显示一条主建议和两条备选。例如：

- “人物和桌子都集中在画面右侧；可以把桌子移到左后方，增加关系张力。”
- “85mm 与当前狭小空间会压缩纵深；如果想保留环境，可尝试 35mm。”
- “主光在人物正面，面部会较平；可以把灯位移到左前 45° 形成明暗层次。”

建议必须提供“应用”“换一个”“忽略”。只有明确可映射到现有控制的建议才出现“应用”。

### 3. 模型提供的拍后建议

用户拍下参考图后，提供一个明确但非强迫的入口“帮我想想”，模型可基于图像、场景事实和用户备注返回：

- 画面观察；
- 三个不同方向，而不是一个标准答案；
- 一个最值得用户回答的追问；
- 可选的下一镜头衔接建议。

建议方向可分为“强化当前情绪”“制造反差”“推进故事”。用户接受某方向后才写入 `CreatorIntent` 或 `PromptDraft`。

### 4. 引导式提问

避免一次展示完整编剧问卷。每次只问一个对当前信息增益最高的问题，例如：

- “你更想让观众注意这个人，还是注意他和空间的距离？”
- “这段安静是安全，还是压抑？”
- “下一个镜头需要延续这种距离，还是突然靠近？”

问题答案保存为结构化 `CreatorIntent`，而不是仅保留在聊天记录里。

## 六、大语言模型接入架构

### 1. 不从 iOS 直接调用模型供应商

推荐链路：

```text
SceneZeroV2
   → SceneZero API（自有轻量后端）
       → OpenAI Responses API
```

API Key 只能保存在服务端环境变量或密钥管理服务中，不能写进 App、Info.plist、Swift 文件或远程配置。客户端使用自己的匿名会话或账号令牌访问 SceneZero API，并由服务端完成限流、配额、模型选择、Prompt 版本、日志脱敏和故障切换。

### 2. 首批服务端接口

- `POST /v1/prompt-drafts`：生成或增强 `PromptDraft`；
- `POST /v1/creative-suggestions`：返回最多三条建议和一个追问；
- `POST /v1/intent-refinements`：根据用户回答更新 `CreatorIntent`；
- `POST /v1/transcriptions`：后续把语音灵感转为文字，可独立排期。

请求统一包含 `schemaVersion`、`promptVersion`、设备 locale 和幂等键。响应包含模型 ID、模型快照/别名、Prompt 版本、请求 ID、耗时和安全状态，便于排查与评估。

### 3. OpenAI API 选择

- 新项目使用 Responses API；它统一文本与图像输入，并支持后续多轮与工具能力。
- 使用图像输入分析参考图，同时传入结构化场景事实；图像负责补充环境观察，AR 数据负责约束空间事实。
- 使用 Structured Outputs 的严格 JSON Schema 返回 `PromptDraft` 或 `CreativeSuggestionResponse`。
- 小型结构化响应首版不必流式输出；流式 JSON 会增加客户端状态复杂度。将来较长的引导对话可以使用 SSE，并用 Swift `URLSession.AsyncBytes` 消费事件。
- 模型由服务端配置和路由，不硬编码在 App。当前可以用成本敏感模型处理常规建议，用更强模型处理用户主动请求的深度故事梳理；上线时锁定经过评测的模型快照，升级必须先跑回归集。

按 2026-07-13 的官方模型页，GPT-5.6 Luna 面向成本敏感、高吞吐任务，Terra 平衡能力与成本，Sol 面向复杂推理。建议先对 Luna 与 Terra 做真实场景评测，而不是仅凭型号决定默认模型。

### 4. 隐私与上传策略

- 首次使用 AI 画面分析时明确说明将上传哪些内容；
- 默认移除 EXIF、位置和不必要的原图元数据；
- 上传前缩放为满足视觉理解的尺寸，不默认传原始全分辨率；
- 用户可以选择“仅发送场景描述，不发送照片”；
- 服务端不默认长期保存原图，日志只记录哈希、结构化指标和请求错误；
- AI 结果标注为建议，并允许完全关闭在线能力。

### 5. 缓存、成本与可靠性

- 对 `imageHash + sceneSnapshotHash + creatorIntentHash + promptVersion` 做结果缓存；
- 用户快速重复点击时复用同一个幂等请求；
- 失败后显示本地 Prompt，不让保存流程失败；
- 为每个功能设置输入尺寸、输出长度、超时和每日配额；
- 后端提供熔断与可观测性，客户端只接收稳定的 SceneZero 错误码。

## 七、评测先于复杂 Agent

首版不需要 Agents SDK、自动 Web 搜索或多工具代理。SceneZero 当前是边界明确的“图像 + 场景事实 → 结构化建议”任务，单次 Responses API 调用更可控、更便于评测。

先建立至少 24 个固定样例：

- 空场景；
- 单人物；
- 多人物；
- 人物与不同道具关系；
- 单灯与多灯；
- 四种焦距与不同画幅；
- 用户意图为空、明确、矛盾三类；
- 模糊、逆光和包含无关人物的真实图像。

每个结果评估：

1. 事实一致性：有没有改错人物、道具、位置、灯光和镜头；
2. 非虚构：未知内容是否保持未知；
3. 具体性：建议是否能直接执行；
4. 多样性：三个方向是否真正不同；
5. 可控性：用户修改意图后结果是否对应变化；
6. 语言质量：是否避免空泛“电影感”；
7. 延迟和成本。

确定性编译器使用普通单元测试；模型输出使用固定数据集、Schema 校验和人工评分。Prompt、Schema 或模型变更必须跑同一批回归样例。

## 八、不限于 AI 的下一步工作

### P0：完成当前录音闭环

- 真机验证蓝牙/有线输入、音频中断和权限恢复；
- 增加暂停/继续、停止后预听与重录；
- 波形缩略图持久化和详情拖动定位；
- 避免 `try?` 静默吞掉用户操作触发的保存与音频错误。

### P0：数据库与写入链收口

- 建立 Schema V2，而不是继续给 V1 原地加字段；
- 灵感集浏览、移动、排序和重命名切换到 `CollectionMembership`；
- Prompt 与 AR 布局切换到 `PromptDocument` / `ARPrevisualization`；
- 删除或排除 V2 中已经不再使用的 `ProjectView.swift`，减少概念回流。

### P1：Prompt 事实层与本地生成

- 完成相机坐标、关系解析、`SceneSnapshot` 和 `PromptDraft`；
- 为对象位置、灯光、焦距和空场景建立单元测试；
- 让详情页逐字段编辑 Prompt，并显示字段来自“现场 / 用户 / AI”的来源。

### P1：本地创作建议

- 先实现 8–12 条高质量规则；
- 建议只在用户主动打开或场景发生关键变化后更新；
- 记录“应用 / 忽略 / 换一个”，为后续模型评测提供真实偏好数据。

### P2：最小模型后端

- 部署 SceneZero API；
- 接入 Responses API 图像输入和严格结构化输出；
- 完成隐私开关、限流、缓存、错误降级与请求追踪；
- 用 24 个固定样例比较两个候选模型后再选择默认。

### P2：引导式故事发展

- 拍后提供三个方向和一个追问；
- 将回答写入 `CreatorIntent`；
- 支持“下一镜头”建议，但不自动建立完整项目或故事板。

### P3：多模态理解

- 录音转写和摘要；
- 从音乐条目的节奏/情绪标签辅助镜头节奏建议；
- 灵感集级别的主题聚类、时间线回看和“这些记录可能在讲什么”；
- 所有跨灵感分析必须由用户主动触发，并明确本次使用哪些资料。

## 九、建议的最近三个迭代

### Iteration 1：事实可信

交付 `SceneSnapshot`、相机坐标关系、Schema V2、本地 `PromptDraft` 和单元测试。此时不接模型，但 Prompt 已明显优于当前字符串拼接。

### Iteration 2：建议可用

交付本地创作建议、可应用动作、Prompt 字段编辑和来源标记。同步完成录音预听/暂停及真机问题。

### Iteration 3：模型增强

交付最小后端、图像输入、Structured Outputs、三个创作方向和一个追问；完成隐私说明、缓存、降级和固定样例评测。

完成这三个迭代后，再根据真实使用数据决定是否需要持续对话、灵感集级故事梳理、转写或图像生成，而不是一开始把产品做成通用 AI 聊天工具。

## 十、Iteration 1 完成后的修订方案（事实可信之后）

### 1. 新基线判断

“事实可信”核心已经落地：快门冻结、相机坐标、空间关系、本地 `PromptDraft`、统一渲染器、`ARPrevisualization` / `PromptDocument` 写入和详情页来源显示都已完成。因此上文 Iteration 1 中这些项目视为已完成，下一轮不再重复重构。

需要注意：本轮新领域模型编码进现有 `layoutData` 和 `structuredData`，并没有新增或删除 SwiftData 的持久化属性。从数据库角度看，这次变化主要是 **blob 内容版本变化**，不是必须立刻创建 Schema V2 的结构变化。不要为了“Iteration 2”这个产品迭代名称强行制造数据库版本。

### 2. 数据库版本策略先做决策门

在修改 SwiftData 模型之前，先明确 V2 开发数据是否需要保留：

#### 路径 A：V2 数据仍可丢弃（当前更推荐）

- 保留原 `SceneZero` Demo 和它的 Bundle ID，不受影响；
- 删除设备/模拟器上的 `SceneZeroV2` 开发数据或重装 V2；
- 把当前完整模型定义整理成正式、可冻结的首个发布 Schema；
- 从此以后不再修改历史 Schema 中的模型定义，新字段只进入下一版本；
- 建立“旧 Schema 文件只读”的工程约定和测试。

这是开发期成本最低、风险最小的方案。版本号可以继续叫 `SceneZeroSchemaV1`，因为产品迭代 2 不等于数据库 Schema 2。

#### 路径 B：必须保留现有 V2 数据

- 先备份并导出一份真实 V2 store 测试样本；
- 从当前可运行模型冻结精确的 V1 类型快照；
- 新建独立的最新 Schema 模型类型，显式处理实体原名和关系；
- 使用正式 `SchemaMigrationPlan` 在复制的数据上验证，而不是直接在唯一真机数据上尝试；
- 验证条数、关系、媒体路径、Prompt 解码和回滚后，再切换 App 容器。

在没有历史模型快照和数据库样本时，不应声称迁移安全。若选择路径 B，应将它单独作为一次数据库工程任务，不与 UI 或创作建议混合提交。

### 3. Prompt 数据 blob 也需要自己的版本迁移

即使 SwiftData Schema 不变，`SceneSnapshot` 和 `PromptDraft` 的 Codable 结构未来仍会变化。需要补充：

- `SceneSnapshot.schemaVersion` 与 `PromptDraft.schemaVersion`；
- `SceneSnapshotDecoder` / `PromptDraftDecoder`，按内容版本解码；
- 对未知版本返回可理解错误并回退 `canonicalText`，不能直接静默返回空 Prompt；
- 每次重新编译 Prompt 时记录 `compilerVersion` 与 `rendererVersion`；
- 用 fixture 保存至少一份每个内容版本的 JSON/Data，作为向后兼容测试。

SwiftData Schema 版本解决“表结构变化”，内容 Schema 版本解决“Data 内部 JSON 变化”，两者不要混用。

## 十一、P0：将 CollectionMembership 切为事实来源

### 1. 先确定产品语义

建议正式支持“一条灵感属于多个灵感集”，因为同一照片、录音或事件可能同时服务于不同故事与情绪主题：

- “所有灵感”是查询结果，不创建 membership；
- “收藏”继续由 `isFavorite` 派生，不创建伪灵感集；
- 自定义灵感集通过 `CollectionMembership` 建立多对多关系；
- `CollectionMembership.sortIndex` 表示该灵感在当前灵感集内的顺序；
- 灵感可以暂时不属于任何自定义灵感集，但仍存在于“所有灵感”中，不称为“待整理”。

### 2. 建立唯一数据访问层

新增 `InspirationCollectionRepository` 或扩展现有 service，所有页面不再直接修改 `entry.boardName`。至少提供：

- `collections(containing:)`
- `entries(in:)`
- `add(_:to:)`
- `remove(_:from:)`
- `replaceMemberships(for:with:)`
- `reorder(_:in:)`
- `rename(_:)`
- `deleteCollection(_:keepingInspirations:)`
- `backfillLegacyMemberships()`

所有用户触发的保存错误必须返回 UI；当前若干 `try? modelContext.save()` 和 `try? assign(...)` 会造成界面显示成功但关系未落库，应在这轮消除。

### 3. 幂等 backfill

从兼容字段建立 membership：

1. 遍历 `Inspiration.boardName` 非默认值的旧灵感；
2. 按规范化名称查找或创建 `InspirationCollection`；
3. 若相同 inspiration/collection 关系已存在则跳过；
4. 将 `Inspiration.sortIndex` 写入 membership；
5. 保存 backfill 版本标记，重复启动不会重复创建；
6. 输出诊断统计：扫描、创建、跳过、冲突和失败数量。

不要把 backfill 放在每次页面 `.task` 中长期运行；完成后应由持久化版本标记短路。

### 4. 分步切换，避免一次性失联

1. **补齐数据**：继续旧读 + 双写，运行 backfill；
2. **影子校验**：同一页面同时计算旧字段结果和 membership 结果，只记录差异；
3. **切换读取**：灵感集卡片数量、详情、移动、重命名和排序全部改读 membership；
4. **停止旧写**：`boardName/sortIndex` 只保留兼容投影；
5. **后续 Schema 才删除旧字段**。

### 5. 必须覆盖的测试

- backfill 重复运行不产生重复 membership；
- 同一灵感加入两个灵感集；
- 从一个灵感集移除后仍保留在另一个以及“所有灵感”；
- 删除灵感集只删除 membership，不删除灵感和媒体；
- 删除灵感时级联删除所有 membership；
- 灵感集重命名不需要遍历修改灵感；
- 每个灵感集的排序相互独立；
- 收藏状态不受 membership 改动影响。

## 十二、P0：收紧 PromptDocument 写入与编辑

### 1. PromptDocument 成为唯一 Prompt 事实来源

- 新条目必须有一个明确的 active `PromptDocument`；
- `canonicalText` 由 `PromptRenderer` 生成，不允许 UI 自己拼接；
- `Inspiration.prompt` 仅为旧页面兼容投影；
- 详情页找不到或无法解码结构化数据时显示“使用兼容文本”，而不是伪装成正常结构化 Prompt；
- 增加结构化数据损坏 fixture，验证回退路径。

### 2. 不要在每个字符变化时直接落库

当前修改备注会同步更新 PromptDocument，方向正确，但应避免每次键入都编码、更新 SwiftData 并保存。建议：

- UI 使用独立 `@State` 编辑草稿；
- 300–500ms 可取消 debounce 后在内存重新编译预览；
- 失去焦点、点击完成或离开页面时再持久化；
- 保存失败保留编辑草稿并明确提示重试；
- 取消旧 Task，避免较早结果覆盖较新的备注。

### 3. 增加生成元数据

在下一次真正修改持久化模型时，为 PromptDocument 规划：

- `status`：draft / active / archived / failed；
- `compilerVersion`、`rendererVersion`；
- `sourceSnapshotID`；
- `inputHash`，判断 Prompt 是否因输入变化而过期；
- `generationSource`：local / model / userEdited；
- `modelIdentifier` 与 `remoteRequestID`（接模型后使用）。

这些字段确实会改变持久化 Schema，应与正式数据库版本升级一起设计，而不是现在零散加入 V1。

## 十三、Iteration 2：先做本地创作建议

### 1. 建立规则引擎而不是继续扩展三元文案

新增纯 Swift `LocalCreativeAdvisor`，输入 `SceneSnapshot + CreatorIntent`，输出 `[CreativeSuggestion]`。首批规则控制在 8–12 条，并覆盖：

- 主体过度集中在同一侧；
- 主体与关键道具空间关系不清；
- 85mm 与狭小空间导致环境信息弱；
- 24mm 接近主体可能造成夸张透视；
- 正面单灯使层次偏平；
- 逆光但没有补光；
- 多灯方向冲突；
- 想表达疏离但主体距离过近；
- 想表达压迫但画面留白和纵深过强；
- 无人物时提示考虑环境作为主体，而不是要求添加人物。

### 2. 建议必须可解释、可执行

每条建议包含：观察、建议、理由、来源、探索等级和可选 action。只有能安全映射到当前设置的 action 才显示“应用”，例如切换 35mm、降低灯光强度；涉及移动 AR 对象时先聚焦对应实体，由用户确认位置，不能瞬移对象破坏预演。

### 3. 触发与 UI

- 场景关键状态变化后 debounce 500–800ms；
- 默认只显示一条，不自动轮播；
- 灯泡按钮打开最多三条建议；
- 提供“应用 / 换一个 / 忽略”；
- 记录 suggestion rule ID 与结果，不保存不必要的完整现场图；
- VoiceOver 先读观察，再读建议，action 使用明确动词。

### 4. 测试优先

每条规则至少有一个命中和一个不命中测试；另外验证冲突建议去重、优先级、最大数量和相同场景输出稳定。完成这些测试后再接远程模型，否则无法判断模型是否真的比本地规则更好。

## 十四、Iteration 3 前的最小模型准备

在本地建议完成后，再实现模型后端。客户端此时只需要抽象：

- `CreativeAdvising` protocol；
- `LocalCreativeAdvisor`；
- 后续 `RemoteCreativeAdvisor`；
- `CreativeAdviceCoordinator` 负责本地立即返回、远程可选增强、取消、超时与降级。

远程结果不能直接覆盖本地事实或用户意图，只能生成新的候选建议或 `PromptDraft` 变体。第一版仍采用一次性结构化请求，不做持续聊天、不引入 Agent 框架。

## 十七、补充评审：iPhone 取景界面防重叠与取景框扩展

### 1. 当前问题不是图标尺寸，而是布局层级

当前 iPhone 竖屏同时常驻了四组界面：

- 顶部完整建议文字和建议、重置、构图按钮；
- 右上方随工具变化的 2–4 个调节按钮；
- 右侧快门和纵向工具选择器；
- 右下方画幅、焦距、景别信息以及系统 Tab Bar。

这些控件都在争夺同一条右侧纵向空间。当前 `cameraControls` 又以屏幕中心为基准分别计算调节列、快门和工具选择器的偏移，因此小屏 iPhone、较大动态字体或较高的底部安全区都会放大碰撞风险。单纯把图标从 44pt 缩小不能解决问题，也会破坏 Apple 建议的 44×44pt 最小触控区域。

取景框偏小也与同一布局有关。`framingContentInsets` 在 iPhone 竖屏为右侧工具轨预留了接近 100pt，`FramingGeometry` 又在剩余区域内按宽度 4%、高度 8% 二次缩进；中景、近景还会通过 `shotType.framingScale` 再次缩小取景框。结果是界面控件和取景框互相挤压。

### 2. 定稿方向：相机画面优先，手机与 iPad 使用不同控制布局

#### iPhone 竖屏

取消常驻的右侧纵向工具轨，改成三层轻量控制：

1. **顶部状态层**：左侧保留一条可截断的状态胶囊；有建议时轻点状态胶囊直接打开建议。右侧只常驻构图辅助线和“更多”两个 44pt 按钮，重置场景放入“更多”菜单。
2. **底部镜头层**：画幅、焦距、景别合并成唯一的居中信息胶囊，轻点打开现有 `LensSettingsSheet`。
3. **底部拍摄层**：中间为 68pt 快门，左侧为当前工具按钮，右侧为当前工具的调节入口。轻点工具按钮后用短横向工具条或底部 Sheet 选择人物、道具、画面、灯光；轻点调节入口后只展示当前工具相关选项。

默认状态只显示一个工具入口、一个快门和一个调节入口，不同时展示四个工具及四个灯光参数。选择完成后自动收起，符合渐进披露原则。

#### iPhone 横屏与 iPad

- iPhone 横屏可使用缩短后的侧边工具轨，但顶部状态文字应限制宽度；
- iPad 和足够宽的窗口可以继续使用右侧纵向工具轨；
- 不按设备名称判断，而是根据 `GeometryProxy` 的有效宽高和 size class 生成 `CaptureLayoutMode`；
- 建议至少区分 `.phonePortrait`、`.phoneLandscape`、`.regularSideRail` 三种布局。

### 3. 扩大取景框的具体方式

#### 3.1 控件不再参与左右取景边界计算

iPhone 竖屏的 `framingContentInsets` 建议改为：

- top：约 68–76pt，避开状态栏和顶部控制；
- leading / trailing：各 12pt，不再为右侧工具轨预留快门宽度；
- bottom：约 88–104pt，为底部拍摄控制保留基本可读空间；
- 底部控件允许覆盖在预览的低优先级区域上，而不是继续缩小整个取景框。

以 390pt 宽的 iPhone 为例，9:16 取景框目标宽度应达到屏幕宽度的约 88%–94%，而不是当前截图中约四分之三的宽度。

#### 3.2 取消比例式二次留白

`FramingGeometry.frameRect` 当前使用：

```swift
usableBounds.insetBy(
    dx: usableBounds.width * 0.04,
    dy: usableBounds.height * 0.08
)
```

建议改为由布局模式传入固定且可预测的 8–12pt 内边距。比例式纵向 8% 在高屏 iPhone 上会无意义地损失大量空间。

#### 3.3 景别不再改变取景框尺寸

画幅决定裁切边界；远景、中景、近景描述主体在画面中的尺度。当前用 `shotType.framingScale` 缩放实际 `frameRect` 会让同一个 9:16 画幅在选择近景后突然变小，也会改变保存裁切范围。

建议：

- `FramingGeometry.frameRect` 只由 viewport、画幅比例和安全内边距决定；
- `ShotType` 继续进入 Scene Snapshot 和 Prompt；
- 如需给新手提示景别，可增加不影响裁切的主体参考线或人物轮廓，不修改画幅框；
- 屏幕预览与 `FramingOverlayService.croppedReferenceImage` 必须继续使用同一个 frame rect，避免所见与保存结果不一致。

### 4. SwiftUI 重构步骤

#### P0：先解决碰撞

1. 在 `MainView` 新增 `CaptureLayoutMode` 和集中式 `CaptureLayoutMetrics`，统一管理顶部、底部、快门、工具和取景安全区域；不要继续在多个函数中分别计算 offset。
2. 将 `controlsOverlay` 拆为 `phonePortraitControls` 与 `sideRailControls`。
3. iPhone 竖屏移除常驻 `AdjustmentButtonColumn + ToolModePicker` 组合，替换为底部紧凑控制区。
4. 顶部 `topBar` 拆成状态胶囊和最多两个操作按钮；状态胶囊自身承担打开创作建议的交互。
5. 保留 44×44pt 触控区域及至少 8pt 间距；只能缩小视觉图标，不能缩小可点击区域。

#### P1：扩大取景框并统一几何事实

1. 重写 `framingContentInsets`，iPhone 竖屏不再计算 `trailingReserve = trailingPadding + shutterSize + ...`。
2. 为 `FramingGeometry.frameRect` 增加明确的固定边距输入，移除 4% / 8% 二次缩进。
3. 从 frame rect 计算中移除 `shotType.framingScale` 和 `framingYOffset`；若保留景别指引，单独建立 guide geometry。
4. 确认预览框、快门冻结时使用的 viewport/insets、最终图片裁切继续共享同一份几何结果。

#### P2：交互收尾

1. 工具和参数面板出现/收起使用 180–250ms 的可中断动画；选择后自动收起。
2. 轻点画面空白可收起当前参数面板，但不能把关键功能做成只有手势才能发现。
3. 工具按钮增加明确的 `accessibilityLabel`、选中状态和 VoiceOver 顺序。
4. Dynamic Type 较大时顶部状态允许隐藏正文、只保留状态图标；完整内容仍能在建议 Sheet 中读取。
5. ARKit 的 “Move iPhone to start” 属于追踪引导状态，应保证它出现时临时降低其他非必要控件的强调度，避免与取景控制争夺注意力。

### 5. 验收标准

- 375×667、390×844、430×932 三档 iPhone 竖屏均不存在控件相交；
- iPhone 横屏、iPad 竖屏和横屏均有明确的自适应布局；
- 所有操作触控区域不小于 44×44pt，相邻目标间距不小于 8pt；
- 9:16 取景框在 390pt 宽设备上至少占 88% 屏幕宽度；
- 切换远景、中景、近景不会改变画幅框和最终裁切尺寸；
- 16:9、2.39:1、1:1、9:16 的预览比例与保存结果一致；
- 最大 Dynamic Type、VoiceOver、底部 Home Indicator 和系统 Tab Bar 下均无重叠；
- 取景页默认最多出现顶部状态、底部镜头信息、底部拍摄控制三组视觉区域，不再出现贯穿半屏的右侧按钮列。

这轮不建议先做“用户自由拖动取景框大小”。取景框代表最终输出裁切，任意缩放会让画幅比例、预览和保存语义变得不稳定。应先让系统依据屏幕和画幅自动最大化，之后若仍需要更沉浸的查看方式，再增加有明确退出入口的“隐藏控件 / 纯净取景”模式。
